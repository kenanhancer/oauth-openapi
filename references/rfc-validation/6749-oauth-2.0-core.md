# RFC 6749 — The OAuth 2.0 Authorization Framework

Source: https://datatracker.ietf.org/doc/html/rfc6749
Audit date: 2026-05-10

Note on scope: The audited spec (`oauth-openapi.yaml`) explicitly applies
OAuth 2.1 defaults (its own §"Modeling notes"). Therefore the Implicit
(`response_type=token`) and Resource Owner Password Credentials
(`grant_type=password`) grants — though normative in RFC 6749 §4.2 and §4.3
— are intentionally omitted and treated as NOT APPLICABLE rather than as
gaps. Findings below focus on items that RFC 6749 still requires for the
flows the spec retains (`authorization_code`, `client_credentials`,
`refresh_token`) and for the global protocol surface (errors, headers,
client auth, response shapes).

---

## Correctly modeled

- **Authorization endpoint exists** (`GET /authorize`) with `response_type`,
  `client_id`, `redirect_uri`, `scope`, `state` parameters in the query
  string (RFC 6749 §3.1, §4.1.1).
- **Token endpoint exists** (`POST /token`) accepting
  `application/x-www-form-urlencoded` (RFC 6749 §3.2).
- **`grant_type` is the dispatch field** at the token endpoint (RFC 6749
  §3.2) and the spec uses an OpenAPI `discriminator` keyed on it.
- **Authorization Code grant** request body covers `grant_type=authorization_code`,
  `code`, `redirect_uri`, `client_id` (RFC 6749 §4.1.3).
- **Client Credentials grant** request body covers `grant_type=client_credentials`,
  `scope` (RFC 6749 §4.4.2).
- **Refresh Token grant** request body covers `grant_type=refresh_token`,
  `refresh_token`, optional `scope` (RFC 6749 §6).
- **Successful token response** carries `access_token` (REQUIRED),
  `token_type` (REQUIRED), `expires_in`, `refresh_token`, `scope` —
  matching RFC 6749 §5.1.
- **Token response sets `Cache-Control: no-store` and `Pragma: no-cache`
  headers** (RFC 6749 §5.1).
- **Error response object** with `error` (REQUIRED), `error_description`,
  `error_uri` (RFC 6749 §5.2).
- **Error code enum** includes the §5.2 token-endpoint values:
  `invalid_request`, `invalid_client`, `invalid_grant`,
  `unauthorized_client`, `unsupported_grant_type`, `invalid_scope`; and the
  §4.1.2.1 / §4.2.2.1 authorization-endpoint values: `access_denied`,
  `unsupported_response_type`, `server_error`, `temporarily_unavailable`.
- **Error response includes `state`** (returned with authorization-endpoint
  errors per RFC 6749 §4.1.2.1).
- **Client authentication via HTTP Basic** (`clientSecretBasic` security
  scheme) is modeled as the preferred method (RFC 6749 §2.3.1).
- **Client authentication via request body** (`client_id` /
  `client_secret` form fields) acknowledged via `clientSecretPost`
  (RFC 6749 §2.3.1, NOT RECOMMENDED but defined).
- **Public clients permitted without authentication** at `/token` for
  flows where applicable (RFC 6749 §2.3 / §3.2.1; modeled as `none`).
- **`scope` documented as space-delimited** (RFC 6749 §3.3).
- **`state` documented as opaque, anti-CSRF** (RFC 6749 §10.12).
- **HTTPS required** — server URL uses `https://` template (RFC 6749 §3.1
  requires TLS for the authorization endpoint, §3.2 for the token endpoint).
- **`redirect_uri` documented as required when more than one is registered**
  (RFC 6749 §3.1.2.3).

## MISSING — must add to the spec

- **`/authorize` 400 response for `invalid_request` / `unauthorized_client`
  / `unsupported_response_type` / `invalid_scope` returned WITHOUT a
  redirect** (RFC 6749 §4.1.2.1 third paragraph): when `redirect_uri` is
  missing, invalid, or mismatched, the server MUST NOT redirect and MUST
  inform the resource owner. The current spec only models a `302` (redirect
  with error) and `200` (HTML). Add a `400` response on `GET /authorize`.

- **`token_type` value space is RFC-constrained, not free-form** (RFC 6749
  §5.1, §7.1): "value is case insensitive". The spec types it as plain
  `string` without acknowledging case-insensitivity or pointing to the
  IANA OAuth Access Token Types registry. Add an `enum` example list
  (`Bearer`, `mac`, `DPoP`) AND note `x-ms-case-insensitive: true` (or a
  description note) so client codegen does an `equalsIgnoreCase` match.

- **`error_description` character restriction** (RFC 6749 §5.2): values for
  `error`, `error_description`, and `error_uri` MUST NOT include characters
  outside the set `%x20-21 / %x23-5B / %x5D-7E` (i.e. printable ASCII minus
  `"` and `\`). Add a `pattern` or at minimum a description note on
  `ErrorResponse.error_description` and `ErrorResponse.error`.

- **`error_uri` character restriction** (RFC 6749 §5.2): values MUST conform
  to URI-reference per RFC 3986 AND are restricted to
  `%x21 / %x23-5B / %x5D-7E`. Add a `pattern` note (the existing
  `format: uri` does not capture the printable-ASCII restriction).

- **`401 Unauthorized` on `/token` MUST include the `WWW-Authenticate`
  response header** when client authentication via the Authorization
  request header field was attempted (RFC 6749 §5.2, error
  `invalid_client`). The spec returns `401` from `/token` but does not
  declare a `WWW-Authenticate` response header. Add it.

- **Refresh-token response MAY include a new `refresh_token`** (RFC 6749
  §6): "the authorization server MAY issue a new refresh token, in which
  case the client MUST discard the old refresh token". The shared
  `TokenResponse` covers this implicitly, but refresh-token rotation is a
  normative behavior worth a description note on `RefreshTokenRequest` /
  `TokenResponse.refresh_token`.

- **Authorization request response — `code` and `state` are returned in
  the redirect's query** (RFC 6749 §4.1.2): the spec describes the
  `Location` header free-form. Add explicit named query parameters as
  documentation (e.g. an `x-redirect-parameters` extension or a structured
  description listing `code` REQUIRED, `state` REQUIRED-if-present-in-request).

- **`access_token` and `token_type` are REQUIRED in 5.1**, already modeled,
  but `expires_in` is RECOMMENDED with normative wording: "If omitted, the
  authorization server SHOULD provide the expiration time via other means
  or document the default value." Add this nuance to the description.

- **Public-client `client_id` REQUIRED at the token endpoint when no
  client authentication is performed** (RFC 6749 §3.2.1, §4.1.3 fourth
  bullet "REQUIRED, if the client is not authenticating with the
  authorization server"). Spec marks `client_id` as merely optional on
  `AuthorizationCodeTokenRequest`. Strengthen the description (or add a
  conditional schema) to say it is REQUIRED for public clients.

## WRONG — must fix

- **`redirect_uri` on `/authorize` typed as `format: uri`** (RFC 6749 §3.1.2):
  "The redirection endpoint URI MUST be an absolute URI as defined by [RFC3986]
  Section 4.3." `format: uri` allows relative references; change to
  `format: uri-reference` is *worse*, instead either keep `format: uri` and
  add a description note "MUST be absolute URI" + a `pattern` like
  `^[a-zA-Z][a-zA-Z0-9+.-]*:` to require a scheme. Same fix needed on
  `AuthorizationCodeTokenRequest.redirect_uri`.

- **`redirect_uri` MUST NOT include a fragment component** (RFC 6749 §3.1.2):
  not constrained anywhere. Add note + pattern `^[^#]*$`.

- **`scope` parameter syntax** (RFC 6749 §3.3 ABNF): `scope = scope-token *( SP scope-token )`,
  `scope-token = 1*( %x21 / %x23-5B / %x5D-7E )` — i.e. one or more
  printable ASCII tokens excluding `"` and `\`, joined by single spaces.
  The spec's `scope` is plain `string` with no `pattern`. Add the ABNF as a
  `pattern` (e.g. `^[\\x21\\x23-\\x5B\\x5D-\\x7E]+( [\\x21\\x23-\\x5B\\x5D-\\x7E]+)*$`).

- **`response_type` enum on `/authorize`** (RFC 6749 §3.1.1): the RFC
  registers `code` and `token`. The spec's enum lists
  `code`, `id_token`, `code id_token`, `code token`, `code id_token token`
  but **omits `token`**. Even though `token` (Implicit) is deprecated by
  OAuth 2.1, the parameter value `code token` is included — which is
  inconsistent. Either document this as deliberately OAuth-2.1-only or
  add `token` for completeness with RFC 6749. Recommended: leave as is,
  but add a description note "RFC 6749 §4.2 also defines `token` for the
  Implicit grant; intentionally omitted per OAuth 2.1."

- **Token request `Content-Type`** (RFC 6749 §3.2 / §4.1.3): "The client
  MUST use the HTTP `POST` method... using the
  `application/x-www-form-urlencoded` format." Spec is correct for
  `requestBody`. However, parameters MUST appear with `UTF-8` character
  encoding — no acknowledgement in the description. Minor; add a note on
  `/token` description.

- **`error` field "Single ASCII error code" description is incomplete**
  (RFC 6749 §5.2): the RFC defines `error = error-code` with
  `error-code = 1*NQCHAR`, where `NQCHAR = %x21 / %x23-5B / %x5D-7E`.
  Add a `pattern` rather than just a free-text description, and ensure
  the enum is closed (it currently mixes 6749, 6750, 8628, 9449, 8707
  values into one enum — that is fine for a multi-RFC umbrella spec, but
  call out in the description that 6749 §5.2 defines only the first six
  token-endpoint values + the four authorization-endpoint values).

- **Authorization request response delivery** (RFC 6749 §4.1.2 vs §4.2.2):
  for `response_type=code`, parameters MUST be added to the
  `redirect_uri`'s query component using
  `application/x-www-form-urlencoded`. The spec's `Location` header
  example uses `?` query — correct — but does not document the encoding
  rule. Add a note to the `302` response description.

## NICE-TO-HAVE

- Add an `examples` map for the standard `Authorization: Basic <b64>`
  header on `clientSecretBasic` (RFC 6749 §2.3.1 prescribes
  `application/x-www-form-urlencoded` percent-encoding of `client_id` and
  `client_secret` BEFORE base64 — a common implementation bug).
- Document RFC 6749 §3.1.2.4 "Invalid Endpoint" handling: server SHOULD
  respond with HTTP 400 and inform the resource owner.
- Make `state` appearance on the redirect explicitly tied to its presence
  in the authorization request (RFC 6749 §4.1.2: "REQUIRED if the `state`
  parameter was present in the client authorization request").
- Note in `TokenResponse.scope` description that it is REQUIRED when the
  granted scope differs from the requested scope, OPTIONAL otherwise
  (RFC 6749 §5.1).
- Provide an example error JSON body on the `OAuthError` response.
- Mark the `Authorization` header on the token endpoint as a request
  header parameter (currently only modeled via `securitySchemes`); some
  codegen tools require it explicit.
- Add a `503` response example for `temporarily_unavailable`.

---

## NOT APPLICABLE

- **RFC 6749 §4.2 Implicit Grant** (`response_type=token`,
  `grant_type=` n/a): intentionally excluded by the spec's OAuth 2.1
  posture. Documented in the spec's own modeling notes.
- **RFC 6749 §4.3 Resource Owner Password Credentials**
  (`grant_type=password`): same — intentionally excluded per OAuth 2.1.
- **RFC 6749 §3.1 "The endpoint URI MAY include an
  `application/x-www-form-urlencoded` formatted query component"** is a
  server-implementation concern; OpenAPI cannot meaningfully model
  vendor-specific path layouts (the spec already says paths are
  vendor-defined and discovered via `/.well-known/...`).
- **RFC 6749 §3.2.1 second paragraph — alternative client authentication
  schemes**: covered via `clientAssertion` (RFC 7521/7523 are out of
  6749's mandatory scope).
- **RFC 6749 §10 Security Considerations** (TLS, brute force, CSRF, code
  reuse, etc.): largely operational guidance not directly modelable in
  OpenAPI; the spec's HTTPS-only servers entry and PKCE-mandatory posture
  cover the schema-relevant pieces.
- **RFC 6749 §11 IANA Considerations** (registries): not a protocol
  surface item.
