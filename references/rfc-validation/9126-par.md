# RFC 9126 — OAuth 2.0 Pushed Authorization Requests (PAR)

Source: https://datatracker.ietf.org/doc/html/rfc9126
Audit date: 2026-05-10

Scope reviewed: `paths./par`, `paths./authorize` (the `request_uri` parameter
flow defined in §4), `components.schemas.PARRequest`,
`components.schemas.PARResponse`, `components.parameters.RequestUri`,
`components.schemas.ErrorResponse`, `components.schemas.DiscoveryDocument`
(`pushed_authorization_request_endpoint` and
`require_pushed_authorization_requests`), security schemes used by `/par`.

All section references (§) refer to RFC 9126 verbatim.

---

## Correctly modeled

- **Endpoint method, URI, and content type** (§2, §2.1): `/par` is `POST`
  with `application/x-www-form-urlencoded` request body — matches RFC 9126
  "accepts HTTP 'POST' requests with parameters in the HTTP request message
  body using the 'application/x-www-form-urlencoded' format" (§2).
- **HTTPS-only** (§2 third paragraph): "The PAR endpoint URL MUST use the
  'https' scheme" — satisfied via the global `https://{issuer}` server
  template (no per-endpoint modeling needed).
- **Successful response status code is 201 Created** (§2.2): "the server MUST
  generate a request URI and provide it in the response with a '201' HTTP
  status code". Spec uses `'201'` (not `'200'`) — correct.
- **Response body includes `request_uri` and `expires_in` as required**
  (§2.2): `PARResponse.required: [request_uri, expires_in]`.
- **Response media type is `application/json`** (§2.2): modeled on the 201
  response.
- **Example `request_uri` uses the recommended URN form** (§2.2): the
  `examples` value
  `urn:ietf:params:oauth:request_uri:6esc_11ACC5bwc014ltc14eY22c` matches the
  optional `urn:ietf:params:oauth:request_uri:<reference-value>` format
  registered in §9.3.
- **Request body carries the standard authorization-request parameters**
  (§2.1): `PARRequest` lists `response_type`, `client_id`, `redirect_uri`,
  `scope`, `state`, `code_challenge`, `code_challenge_method`, `nonce`,
  matching the "typical parameter set" enumerated in §2.1.
- **`client_id` is REQUIRED in the pushed request** (§2.1 last sentence:
  "as a required authorization request parameter, it is similarly required
  in a pushed authorization request"): listed in `PARRequest.required`.
- **`response_type` is required** (§2.1 implicit via 6749 §4.1.1):
  listed in `PARRequest.required`.
- **`additionalProperties: true` on `PARRequest`** (§2.1): correctly allows
  "any of the parameters applicable for use at the authorization endpoint,
  including those defined in [RFC6749] as well as all applicable extensions".
- **JAR `request` parameter is supported** (§3): `PARRequest.request`
  documented as "Optional signed JWT request object (JAR, RFC 9101)".
- **Standard error response shape** (§2.3 → 6749 §5.2): `400` and `401` map
  to `OAuthError`/`ErrorResponse`.
- **`request_uri` parameter exists at `/authorize`** (§4): `parameters/RequestUri`
  is defined and referenced from the `/authorize` operation, with description
  "Reference to a request previously submitted via PAR (RFC 9126 §4)".
- **AS metadata `pushed_authorization_request_endpoint`** (§5):
  modeled in `DiscoveryDocument.pushed_authorization_request_endpoint` as
  `string, format: uri`.
- **AS metadata `require_pushed_authorization_requests`** (§5):
  modeled in `DiscoveryDocument.require_pushed_authorization_requests` as
  `boolean`, with description matching the RFC's intent.
- **Client authentication is required for confidential clients** (§2.1
  "Authenticate the client in the same way as at the token endpoint"):
  `/par` declares `clientSecretBasic`, `clientSecretPost`, and
  `clientAssertion` security options, satisfying the requirement.
- **DPoP header documented on `/par`** (cross-spec with RFC 9449): the
  reusable `DPoPHeader` parameter is wired into the operation.

## MISSING — must add to the spec

- **`invalid_request_uri` error code** (RFC 9126 §2.3 references RFC 6749
  §4.1.2.1, which defines this code; it is the canonical error returned
  when a `request_uri` provided to `/authorize` is unknown / expired /
  malformed): not present in `ErrorResponse.error` enum. This is the
  diagnostic the AS returns at `/authorize` when a client passes a stale
  PAR-issued URI per §4 ("An expired 'request_uri' MUST be rejected as
  invalid"). Add `invalid_request_uri` to the enum and tag it with
  `# RFC 9126 / RFC 6749 §4.1.2.1` in a comment.

- **`invalid_request_object` error code** (§3 references RFC 9101 / JAR;
  PAR's `request` parameter inherits all JAR validation errors): not
  present in `ErrorResponse.error` enum. Add `invalid_request_object` so
  servers that reject a malformed signed Request Object pushed to `/par`
  can be modeled.

- **`request_uri` MUST NOT appear in the pushed body** (§2.1 fifth
  paragraph: "The 'request_uri' authorization request parameter is one
  exception, and it MUST NOT be provided"; §2.1 step 2: "Reject the
  request if the 'request_uri' authorization request parameter is
  provided"): the spec's `PARRequest` schema is silent on this (and the
  `additionalProperties: true` flag would actually permit it). Add either
  an explicit `not` constraint on the schema or a description note plus
  `propertyNames` exclusion (`not: {required: [request_uri]}` is the
  cleanest OpenAPI 3.1 way).

- **At `/authorize`, when `request_uri` is used, only `client_id` and
  `request_uri` should be sent** (§4 example shows exactly that pair;
  the practice is reinforced by RFC 9101 §5 which PAR delegates to). The
  spec's `/authorize` operation lists `request_uri` alongside ~14 other
  query parameters with no documentation that they are mutually
  exclusive in the PAR-driven flow. Add an operation-level description
  note: "When `request_uri` is supplied, the client SHOULD send only
  `client_id` + `request_uri`; all other parameters were already pushed
  via `/par` and are referenced by the URI (RFC 9126 §4)."

- **`request_uri` is single-use; expired URIs MUST be rejected** (§4
  paragraph 2: "the client MUST only use a 'request_uri' value once …
  An expired 'request_uri' MUST be rejected as invalid"): this normative
  rule is invisible from the spec. Add a description note on the
  `RequestUri` parameter saying "single-use; the AS MUST reject expired
  values with `invalid_request_uri`".

- **`request_uri` MUST be bound to the client that posted it** (§2.2
  "The 'request_uri' value MUST be bound to the client that posted the
  authorization request"): no description note anywhere — worth surfacing
  on `PARResponse.request_uri` for implementors.

- **`request_uri` MUST contain cryptographically strong randomness** (§2.2:
  "MUST contain some part generated using a cryptographically strong
  pseudorandom algorithm such that it is computationally infeasible to
  predict or guess a valid value"): add a description note on
  `PARResponse.request_uri` referencing RFC 6749 §10.10 entropy
  requirement.

- **`expires_in` value range guidance** (§2.2: "the request URI lifetime
  is at the discretion of the authorization server but will typically be
  relatively short (e.g., between 5 and 600 seconds)"): the field is
  typed as plain `integer` with no `minimum`/`maximum`/example. Add
  `minimum: 1` plus a description noting the typical 5–600-second range.

- **`Cache-Control: no-cache, no-store` response header on the 201**
  (§2.2 example response shows `Cache-Control: no-cache, no-store`):
  the `/token` 201 response declares `Cache-Control: no-store` and
  `Pragma: no-cache`; `/par` does not. Add the same headers (the RFC
  example uses `no-cache, no-store` rather than just `no-store`).

- **Public client support on `/par`** (§2.1 second paragraph:
  "The rules for client authentication as defined in [RFC6749] for token
  endpoint requests, including the applicable authentication methods,
  apply for the PAR endpoint as well"): RFC 6749 §3.2.1 permits
  unauthenticated requests when the client type is public. PAR therefore
  SHOULD permit `none` for public clients (mirroring the `/token` and
  `/device_authorization` operations in this same spec, which both
  declare `- none: []`). Add `- none: []` to `/par` `security` so a
  public PKCE client can post a PAR.

- **`request_uri_parameter_supported` / `require_request_uri_registration`
  interaction note** (§5 last paragraph: "A 'request_uri' value obtained
  from the PAR endpoint is usable at the authorization endpoint regardless
  of other authorization server metadata such as 'request_uri_parameter_supported'
  or 'require_request_uri_registration' [OIDC.Disco]"): the spec doesn't
  model these two OIDC-Discovery fields, but a description note on
  `pushed_authorization_request_endpoint` (or on `RequestUri`) clarifying
  that PAR-issued URIs override that legacy metadata is worthwhile.

- **Additional error status codes 405, 413, 429** (§2.3 explicit list):
  the RFC says "the PAR endpoint can also make use of the following HTTP
  status codes: 405 … 413 … 429". The spec only models `400` and `401`.
  Add `405`, `413`, and `429` responses on `/par` (each can reuse
  `OAuthError` or just describe the condition).

## WRONG — must fix

- **`PARRequest` lists `code_challenge` and `code_challenge_method` as
  optional**, but PKCE is mandatory under OAuth 2.1 (which the spec's
  own modeling notes say it follows). The `/authorize` parameters mark
  both `CodeChallenge` and `CodeChallengeMethod` as `required: true`; the
  pushed counterparts in `PARRequest` carry the same parameter values
  but are not in `PARRequest.required: [client_id, response_type]`.
  Either (a) add `code_challenge` and `code_challenge_method` to
  `PARRequest.required` for consistency with the OAuth 2.1 posture, or
  (b) explicitly note in the description that PKCE applies once the
  pushed request reaches `/authorize`. The current state is internally
  inconsistent.

- **`redirect_uri` typed as `format: uri` on `PARRequest`** (§2.4 +
  RFC 6749 §3.1.2): same issue flagged in the 6749 audit — `format: uri`
  in OpenAPI permits relative references; the value MUST be an absolute
  URI. Add a description note "MUST be an absolute URI" and a `pattern`
  enforcing a scheme. Note that §2.4 *does* allow relaxed exact-matching
  for authenticated clients via PAR; document this nuance in the field
  description rather than weakening the validation.

- **`PARResponse.request_uri` typed as `format: uri`** (§2.2): the value
  is technically a URI, but the recommended URN form
  `urn:ietf:params:oauth:request_uri:<reference-value>` is a `urn:` URI
  whose validation is best documented rather than constrained. Either
  keep `format: uri` (URN is a URI) and add a description note about the
  recommended `urn:ietf:params:oauth:request_uri:` prefix, or split into
  a `oneOf` with the URN form and an arbitrary URI. Currently, the
  description doesn't point to the registered URN namespace at all.

- **`/par` 401 response is documented but not tied to an auth method**
  (§2.3 → 6749 §5.2 `invalid_client`): like the 7009 audit, document
  that 401 maps to `invalid_client` and that the AS SHOULD return
  `WWW-Authenticate` when the client used the `Authorization` request
  header (RFC 6749 §5.2). Add a `WWW-Authenticate` response header on
  the 401.

- **Tag for `/par` says "PAR" only**, but the RFC calls the endpoint the
  "Pushed Authorization Request Endpoint" (§2). Cosmetic — the existing
  tag description "RFC 9126 — Pushed Authorization Requests" already
  covers it; fine as is. (Listed here so a future reviewer doesn't try
  to "fix" the short tag name.)

## NICE-TO-HAVE

- **Document `application/json` `Content-Type` on the 201 response
  explicitly in the 201 description** (§2.2 example) rather than relying
  on the implicit `content.application/json` mapping — improves human
  readability of the spec.

- **Provide an `example` body on `PARRequest`** showing a typical PKCE
  authorization-code push (matches RFC §2.1 example) so generated docs
  render an obvious sample.

- **Provide an `example` body on `PARResponse`** with both a URN and a
  short `expires_in` value (e.g., 90 seconds — matches the RFC's
  introduction example).

- **Cross-link `PARRequest.request` to RFC 9101 §4** (JAR Request Object
  rules). Currently the description just says "Optional signed JWT
  request object (JAR, RFC 9101)" — pointing to the specific section
  helps implementors.

- **Document §2.4 redirect-URI relaxation** in the `/par` operation
  description: authenticated clients pushing through PAR may use
  unregistered `redirect_uri` values per AS policy (§2.4) — a useful
  hint for client developers since this differs from the standard
  6749/2.1 exact-match rule.

- **Add `require_pushed_authorization_requests` as a CLIENT metadata
  field** (§6) if/when this spec ever models a Dynamic Client
  Registration request body. Out of scope today since the spec does not
  cover DCR (RFC 7591), but worth a TODO.

- **Document the `iss` audience guidance** for JWT-based client
  authentication at `/par` (§2 sixth paragraph: "the issuer identifier
  URL of the authorization server according to [RFC8414] SHOULD be used
  as the value of the audience"). A description note on `clientAssertion`
  security scheme would help interop.

- **Surface §7.5 "Request URI Swapping" mitigation** on `/par`
  description: "Clients SHOULD use PKCE, a unique `state`, or OIDC
  `nonce` to prevent request URI swap attacks (RFC 9126 §7.5)."

## NOT APPLICABLE

- **§6 Client Metadata (`require_pushed_authorization_requests` as a
  client field)**: the canonical spec does not model RFC 7591 Dynamic
  Client Registration request bodies, so per-client metadata fields
  belong in a future DCR-specific schema, not in this audit's scope.

- **§7 Security Considerations** (request URI guessing, open redirection,
  request object replay, client policy change, request URI swapping):
  operational guidance that cannot be expressed in OpenAPI shape
  constraints. The relevant entropy + one-time-use rules are surfaced as
  description notes in the MISSING section above; the rest is server
  behavior.

- **§8 Privacy Considerations**: prose, not modelable.

- **§9 IANA Considerations** (registry entries for the metadata fields,
  client metadata field, and the URN sub-namespace
  `urn:ietf:params:oauth:request_uri:`): registry actions, not protocol
  surface. The URN form is captured in the example; the metadata fields
  are captured in `DiscoveryDocument`.

- **§2 paragraph "the PAR endpoint MAY also support sending the set of
  authorization request parameters as a Request Object according to
  [RFC9101]"**: covered by the existing `PARRequest.request` field.

- **§1.1 Conventions and Terminology**: definitional, no schema impact.
