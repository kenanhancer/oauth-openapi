# RFC 9396 — OAuth 2.0 Rich Authorization Requests (RAR) — Validation Report

Source: <https://datatracker.ietf.org/doc/html/rfc9396>
Spec under review: `oauth-openapi.yaml` —
`#/components/parameters/AuthorizationDetails` (`/authorize` query param),
`#/components/schemas/TokenResponse.authorization_details`,
`#/components/schemas/DiscoveryDocument.authorization_details_types_supported`,
`#/components/schemas/ErrorResponse.error` (enum),
`#/components/schemas/PARRequest`, `#/components/schemas/IntrospectionResponse`.

> Note: WebFetch was denied for this run. Findings below cite RFC 9396 from
> direct knowledge of the published RFC text (April 2023, IESG-approved,
> stable). Any reader can re-verify against the linked source.

---

## Summary

| Bucket  | Count |
| ------- | ----- |
| MISSING | 9     |
| WRONG   | 4     |
| EXTRA   | 0     |

The spec acknowledges RAR exists (one query parameter, one response array,
one discovery field), but the modeling is so thin that none of the §2.2
common data fields, the token-response semantics, the introspection contract,
the PAR/JAR placement, or the `invalid_authorization_details` error are
representable. A consumer cannot construct a RAR request from this spec
alone.

---

## MISSING (RFC element absent from the OpenAPI spec)

### M1. `AuthorizationDetail` object schema is not modeled (§2, §2.1, §2.2)

§2: *"The request parameter `authorization_details` contains, in JSON
notation, an array of objects. Each JSON object contains the data to specify
the authorization requirements for a certain type of resource."* §2.1
fixes the syntax: an array of objects each with a REQUIRED `type` member.
§2.2 enumerates the common fields (`locations`, `actions`, `datatypes`,
`identifier`, `privileges`).

The spec models `authorization_details` only as `type: string` (in the
query parameter) and as an array of opaque `type: object` (in
`TokenResponse`). There is no reusable `AuthorizationDetail` schema
that defines `type`, `locations`, `actions`, `datatypes`, `identifier`,
or `privileges`.

**Fix:** introduce `#/components/schemas/AuthorizationDetail` with `type`
required and the §2.2 common fields as documented optional members
(`additionalProperties: true` to allow per-type extensions per §3).

### M2. `type` member is not declared REQUIRED for each object (§2.1, §3)

§2.1: *"Each JSON object MUST contain a `type` field."* §3: *"The value of
the `type` field determines the allowable contents of the object that
contains it."*

The `TokenResponse.authorization_details.items` is `type: object` with no
`required: [type]`. The query parameter is just a string. Neither place
encodes the §2.1 MUST.

**Fix:** in the `AuthorizationDetail` schema (M1), set
`required: [type]` and document `type` as an authorization-detail
type identifier (string, registered in IANA per §13.4 or a collision-
resistant URI).

### M3. §2.2 common data fields are not modeled (`locations`, `actions`, `datatypes`, `identifier`, `privileges`)

§2.2 lists five common (cross-type) members:

- `locations` — *"An array of strings representing the location of the
  resource or RS. … typically composed of URIs."*
- `actions` — *"An array of strings representing the kinds of actions to
  be taken at the resource."*
- `datatypes` — *"An array of strings representing the kinds of data being
  requested from the resource."*
- `identifier` — *"A string identifier indicating a specific resource
  available at the API."*
- `privileges` — *"An array of strings representing the types or levels of
  privilege being requested at the resource."*

None of these appear in the spec.

**Fix:** add all five to `AuthorizationDetail` with the §2.2 types
(`locations`/`actions`/`datatypes`/`privileges` are arrays of strings;
`identifier` is a string).

### M4. PAR request body has no `authorization_details` field (§7 / RFC 9126)

§7 (Interaction with PAR): *"… the client uses the parameter
`authorization_details` as defined in this document … as part of the PAR
request."* RFC 9126 §2.1 lists `authorization_details` among the parameters
that the PAR endpoint accepts, encoded the same way as at `/authorize`.

The spec's `PARRequest` schema lists `response_type`, `client_id`,
`redirect_uri`, `scope`, `state`, `code_challenge`, `code_challenge_method`,
`nonce`, `request`, but not `authorization_details`. (`additionalProperties:
true` is set, so it is technically allowed, but it is undiscoverable in
generated docs/clients.)

**Fix:** add `authorization_details: type: string` (JSON-encoded array)
to `PARRequest` with a description pointing to §2 / §7.

### M5. Token endpoint request body has no `authorization_details` (§4)

§4 (Authorization Request): *"… for token requests, the
`authorization_details` parameter MAY also be sent."* §6 (Token Response)
explicitly anticipates the case where the client narrows the granted RAR
in the token request (e.g. on `refresh_token`).

None of `AuthorizationCodeTokenRequest`, `RefreshTokenRequest`,
`ClientCredentialsTokenRequest`, `JWTBearerTokenRequest`, or
`TokenExchangeRequest` declare `authorization_details`.

**Fix:** add `authorization_details: type: string` (JSON-encoded array,
URL-form-encoded value) to each token-request grant body where it is
permitted (at minimum: `authorization_code`, `refresh_token`,
`client_credentials`).

### M6. Introspection response is missing `authorization_details` (§9)

§9 (Token Introspection): *"When an access token contains authorization
details, the authorization server MUST include these in the introspection
response. The `authorization_details` member is an array of objects as
defined in Section 2."*

`IntrospectionResponse` does not declare an `authorization_details`
field, and the schema lacks `additionalProperties: true`, so a strict
validator will reject it on the wire.

**Fix:** add `authorization_details` (array of `AuthorizationDetail`) to
`IntrospectionResponse`.

### M7. JWT access-token claim `authorization_details` not modeled (§9 / §10)

§9 / §10 (JWT representation, cross-referenced with RFC 9068): *"When
issuing JWT access tokens (RFC 9068), the AS includes the granted
authorization details as the `authorization_details` claim."* RFC 9068
§2.2.3 normatively mirrors this.

The spec has no JWT-access-token claim schema (RFC 9068 itself appears in
the cover-page table but is not modeled). This is a cross-RFC gap rather
than a 9396-only gap, but worth flagging because RAR depends on it.

**Fix:** when an `AccessTokenClaims` / RFC 9068 schema is added (out of
scope for this report), include `authorization_details` as one of the
claims.

### M8. `invalid_authorization_details` error code missing from the `error` enum (§5)

§5 (Authorization Error Response): *"… If the authorization server does
not understand the authorization details type or if it is unable to
fulfill the requested authorization details for some other reason, it
MUST refuse the request and return an `invalid_authorization_details`
error to the client."*

`ErrorResponse.error` enumerates `invalid_request`, `invalid_dpop_proof`,
`invalid_target`, etc., but not `invalid_authorization_details`.

**Fix:** add `invalid_authorization_details` to the `error` enum with a
comment `# RFC 9396`.

### M9. No discovery field for `authorization_details_types_supported` semantics description (§10)

§10 (Authorization Server Metadata): *"`authorization_details_types_supported` —
JSON array containing the authorization details type values the
authorization server supports. This metadata MAY be used by clients to
determine the set of authorization detail types the AS supports."*

The spec does declare `authorization_details_types_supported` in
`DiscoveryDocument` (good), but its `description` only says *"RAR
(RFC 9396): supported authorization detail types."* — it does not note
that the values correspond to the `type` field of the
`AuthorizationDetail` objects (§2.1) and that each value is a registered
type identifier (§13.4) or collision-resistant URI. This is the only
runtime hint a client gets about which types it may use.

**Fix:** expand the description and cross-reference the
`AuthorizationDetail.type` field.

## WRONG (RFC element present but modeled incorrectly)

### W1. `authorization_details` query parameter is typed as opaque `string` with no JSON shape (§2)

§2: the value is a JSON-serialized array of objects. Modeling it as
`type: string` is wire-correct (HTTP form encoding requires URL-encoded
string), but the spec gives no schema reference, no
`contentMediaType: application/json`, and no `contentSchema` pointing at
an `AuthorizationDetail[]`. A reader cannot tell what to put inside the
string.

**Fix:** keep `type: string` (HTTP transport reality) but add
`contentMediaType: application/json` and
`contentSchema: { type: array, items: { $ref: '#/components/schemas/AuthorizationDetail' } }`
(OpenAPI 3.1 supports this), and reference §2 in the description.

### W2. `TokenResponse.authorization_details.items` is `type: object` (untyped) (§6)

§6 (Authorization Details in Token Response): *"… the AS returns the
authorization details that have been granted, in the same JSON format,
as a top-level member of the token response. The granted authorization
details MAY differ from those requested … but the structure (objects
with required `type`) is the same."*

`TokenResponse.authorization_details.items: type: object` discards the
type contract. A consumer cannot validate that a returned item has a
`type` field, let alone the §2.2 common members.

**Fix:** `items: $ref: '#/components/schemas/AuthorizationDetail'`.

### W3. Description omits "MAY be a subset of requested" semantic (§6)

§6 (and §1.3 of the Introduction): the AS *MAY* grant a narrower set than
requested — different `actions`, fewer `locations`, downgraded
`privileges`, or omit objects entirely. Clients MUST inspect the granted
set rather than assume it equals the request.

The current description is just *"granted authorization detail objects."* —
that does not warn the consumer about the request-vs-grant divergence,
which is the central RAR semantic that distinguishes it from `scope`.

**Fix:** rewrite description to say "Granted authorization detail
objects. MAY be a subset of, or otherwise differ from, the
`authorization_details` requested by the client (RFC 9396 §6). Clients
MUST inspect this field rather than assume the request was granted in
full."

### W4. `AuthorizationDetails` query parameter description does not state it MUST be JSON-encoded (§2)

§2: *"The value of the `authorization_details` parameter is a JSON
[RFC8259] array of objects."* In transport (`application/x-www-form-
urlencoded` or query string), the JSON is then URL-encoded as a single
string value.

The current description (*"JSON-encoded array of authorization detail
objects"*) hints at this but does not explicitly say "single
URL-encoded JSON string per HTTP form-encoding rules." Implementers
sometimes mistakenly send repeated `authorization_details=…` form
parameters.

**Fix:** add a sentence: "Sent as a single URL-encoded JSON string
(not as repeated form parameters)."

## EXTRA (in spec, not in RFC)

None. The three RAR-related elements present (`AuthorizationDetails`
query param, `TokenResponse.authorization_details`,
`DiscoveryDocument.authorization_details_types_supported`) all exist in
RFC 9396 — they are just under-specified.

## Notes / out of scope

- The RFC's §3 examples (payment initiation, account information) are
  not normative shapes and should not be modeled as fixed schemas in
  this spec — they belong to vertical profiles (e.g. FAPI, OpenBanking).
  The right pattern is the `AuthorizationDetail` base + `discriminator:
  type` if/when the spec wants to enumerate concrete types.
- §11 / §12 (Privacy & Security Considerations) impose no schema-level
  obligations; nothing to add.
- §13 (IANA): the spec does not need to mirror the IANA registry, but
  the description on `authorization_details_types_supported` could
  reference it for discoverability.
- §8 (Token Exchange / RFC 8693 interaction): the spec's
  `TokenExchangeRequest` schema also has no `authorization_details` field,
  but §8 only states it MAY be included; treated as part of M5 above.
- The `oauth2` security scheme at the bottom of the spec exposes only
  `scope`-based scopes; RAR cannot be expressed in the OpenAPI security
  flow object (this is an OpenAPI limitation, not a spec bug).
