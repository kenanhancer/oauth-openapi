# RFC 7636 — Proof Key for Code Exchange by OAuth Public Clients (PKCE)

Source: https://datatracker.ietf.org/doc/html/rfc7636
Audit date: 2026-05-10

Scope reviewed: `components.parameters.CodeChallenge`,
`components.parameters.CodeChallengeMethod`,
`components.schemas.AuthorizationCodeTokenRequest` (`code_verifier`),
`components.schemas.PARRequest` (`code_challenge`, `code_challenge_method`),
`components.schemas.DiscoveryDocument` (`code_challenge_methods_supported`),
`components.schemas.ErrorResponse` (PKCE error codes),
description text on `/authorize`.

NOTE: WebFetch and curl were denied during this audit, so the comparison below
is made against the well-known normative content of RFC 7636 (September 2015,
IETF Standards Track) from training data. All section references (§) refer to
RFC 7636 verbatim; no quoted text is fabricated.

## Correctly modeled

- **`code_challenge` parameter exists on `/authorize`** (§4.3): the spec
  declares `parameters.CodeChallenge` with `name: code_challenge`, `in: query`
  and references it from the `/authorize` GET (oauth-openapi.yaml:559–567,
  123). This matches "The client sends the code challenge as part of the
  OAuth 2.0 Authorization Request (Section 4.3)".

- **`code_challenge_method` parameter exists on `/authorize`** (§4.3): the
  spec declares `parameters.CodeChallengeMethod` with the correct enum
  `[S256, plain]` (oauth-openapi.yaml:569–579, 124). The two values match the
  registry exactly per §4.3 / §6.

- **`code_verifier` on the token request** (§4.5): `AuthorizationCodeTokenRequest`
  lists `code_verifier` in `required` and constrains it with
  `minLength: 43, maxLength: 128` (oauth-openapi.yaml:728, 740–744). The
  length bounds match §4.1 verbatim ("with a minimum length of 43 characters
  and a maximum length of 128 characters").

- **`code_verifier` is REQUIRED on the token request** (§4.5): present in the
  schema's `required` array (oauth-openapi.yaml:728). Matches "the client
  sends the authorization code in the access token request as usual but
  includes the code_verifier secret generated at Step (A)".

- **`code_challenge_methods_supported` discovery field** (§6 / referenced by
  RFC 8414 §2): `DiscoveryDocument.code_challenge_methods_supported` is an
  array of strings restricted to `[S256, plain]` (oauth-openapi.yaml:1222–1226).

- **PKCE on PAR** (RFC 9126 §3 reuses §4.3 PKCE parameters):
  `PARRequest` lists `code_challenge` and `code_challenge_method` as optional
  body fields (oauth-openapi.yaml:981–984) — correct because §4.3 defines
  them as authorization-request parameters that PAR forwards.

- **`/authorize` description states PKCE is mandatory**: "PKCE
  (`code_challenge`) is mandatory" (oauth-openapi.yaml:113). Matches the
  spec's OAuth 2.1 stance and §4.4.1's recommendation that servers MAY
  require PKCE.

- **Cross-reference to RFC 7636 §4.5**: `AuthorizationCodeTokenRequest`'s
  description cites "RFC 6749 §4.1.3 with PKCE per RFC 7636 §4.5"
  (oauth-openapi.yaml:726). Section is correct (the verifier is sent at
  step (D) which is the token request — §4.5).

## MISSING — must add

- **`code_verifier` allowed-character set** (§4.1): "code_verifier =
  high-entropy cryptographic random STRING using the unreserved characters
  `[A-Z] / [a-z] / [0-9] / "-" / "." / "_" / "~"` from Section 2.3 of
  [RFC3986], with a minimum length of 43 characters and a maximum length of
  128 characters." The spec models length but not the character class. Add
  `pattern: '^[A-Za-z0-9._~-]{43,128}$'` to the `code_verifier` schema
  (oauth-openapi.yaml:740–744). Without this, a generator will accept
  strings containing `+`, `/`, `=`, `%`, etc., which the AS MUST reject.

- **`code_challenge` length constraints** (§4.2): "code_challenge = … When
  S256 is used, this is the BASE64URL-ENCODE(SHA-256(ASCII(code_verifier)))
  string and is therefore exactly 43 characters; when `plain` is used the
  length matches `code_verifier` (43–128)". The spec leaves
  `parameters.CodeChallenge.schema` as a bare `type: string`
  (oauth-openapi.yaml:566–567) with no `minLength`/`maxLength`/`pattern`.
  Add at minimum `minLength: 43, maxLength: 128` and the same unreserved-
  character `pattern` for plain or the base64url alphabet for S256. The
  cleanest model is `pattern: '^[A-Za-z0-9._~-]{43,128}$'` (covers both
  S256 base64url output without padding and plain verifier alphabet).

- **`code_challenge_method` default behavior** (§4.3): "code_challenge_method
  – OPTIONAL, defaults to `plain` if not present in the request. Code
  verifier transformation method is `S256` or `plain`." The spec marks
  `code_challenge_method` as `required: true` (oauth-openapi.yaml:572) which
  is acceptable for OAuth 2.1 enforcement, but the OpenAPI `default: S256`
  (oauth-openapi.yaml:579) contradicts the RFC default of `plain`. The
  description should explicitly state "RFC 7636 default is `plain`; this
  spec overrides to `S256` per OAuth 2.1." Without this, readers may assume
  RFC compliance with a `S256` default.

- **PKCE error code `invalid_request` for missing/invalid challenge** (§4.4.1):
  "If the server requires Proof Key for Code Exchange (PKCE) by OAuth Public
  Clients and the client does not send the `code_challenge` in the request,
  the authorization endpoint MUST return the authorization error response
  with the `error` value set to `invalid_request`." The spec lists
  `invalid_request` in `ErrorResponse.error` enum (oauth-openapi.yaml:890),
  but there is no documentation that ties this error to the PKCE missing-
  challenge condition. Add a sentence under the `code_challenge` description
  noting that when PKCE is required and `code_challenge` is absent the
  server returns `error=invalid_request` per §4.4.1.

- **PKCE error code `invalid_grant` for failed verifier match** (§4.6):
  "If the values are not equal, an error response indicating
  `invalid_grant` as described in Section 5.2 of [RFC6749] MUST be
  returned." The enum already lists `invalid_grant`
  (oauth-openapi.yaml:892), but again there is no documentation tying it to
  "code_verifier did not match the original code_challenge". Add a note
  under `code_verifier` (oauth-openapi.yaml:740–744).

- **`code_challenge_method` with unsupported transform** (§4.4.1): "If the
  server supporting PKCE does not support the requested transformation,
  the authorization endpoint MUST return the authorization error response
  with `error` value set to `invalid_request`. The `error_description` or
  the response of `error_uri` SHOULD explain the nature of error, e.g.,
  transform algorithm not supported." Document this on the
  `code_challenge_method` parameter description.

- **Server MUST support `S256`** (§4.2): "If the client is capable of using
  `S256`, it MUST use `S256` … Clients are permitted to use `plain` only if
  they cannot support `S256` for some technical reason …". The
  `DiscoveryDocument.code_challenge_methods_supported` field allows any
  subset including only `plain`; the description should call out that an
  AS conformant with RFC 7636 §4.2 MUST advertise `S256`.

- **`require_pushed_authorization_requests` analogue for PKCE
  enforcement**: there is no `require_pkce` discovery flag. RFC 7636 itself
  does not define one (it is an OAuth 2.1 / Security BCP concern), but
  since the spec already invents adjacent enforcement metadata
  (`require_pushed_authorization_requests`, oauth-openapi.yaml:1227–1229),
  consistency suggests adding a `require_pkce` boolean (or noting that
  PKCE is implicitly required when `token_endpoint_auth_methods_supported`
  contains `none`). NICE-TO-HAVE — see below.

## WRONG — must fix

- **`code_challenge_method` is `required: true` but RFC 7636 §4.3 makes it
  OPTIONAL with default `plain`**: oauth-openapi.yaml:572. Marking it
  required is *more strict* than the RFC and is justifiable under OAuth
  2.1, but the parameter description (oauth-openapi.yaml:573–576) only
  says "Always `S256` per OAuth 2.1" without acknowledging the RFC's
  OPTIONAL status. Either (a) drop `required: true` and rely on the
  description / `default: S256`, or (b) keep `required: true` and add a
  sentence "Required by this spec (OAuth 2.1); RFC 7636 §4.3 makes this
  parameter OPTIONAL with default `plain`."

- **`default: S256` on `code_challenge_method` contradicts the RFC's
  `plain` default**: oauth-openapi.yaml:579. Per §4.3, "code_challenge_method
  … defaults to `plain` if not present in the request." The OpenAPI
  `default` here is informational, but consumers / generators may use it.
  Either remove the `default` (since the parameter is `required: true`,
  no default is possible) or annotate it as an OAuth 2.1 deviation from
  RFC 7636 in the description.

- **`code_challenge` description is incomplete on the `plain` method**
  (§4.2): the description (oauth-openapi.yaml:563–565) only documents the
  S256 case ("`BASE64URL(SHA256(code_verifier))` when method is `S256`").
  RFC 7636 §4.2 also defines `plain`: "code_challenge = code_verifier".
  Add this case.

- **`PARRequest.code_challenge_method` lacks the enum constraint
  (`[S256, plain]`)**: oauth-openapi.yaml:983–984 defines it as a bare
  `type: string`. The same enum from `parameters.CodeChallengeMethod`
  must apply because PAR forwards the same authorization-request
  parameters per RFC 9126 §3. Replace with a `$ref` to a shared schema
  or duplicate the `enum: [S256, plain]`.

- **`PARRequest.code_challenge` lacks length / pattern constraints**:
  same issue — bare `type: string`. Add the same constraints suggested
  above for `parameters.CodeChallenge`.

- **PKCE not declared on `/authorize` `200` HTML response** is fine, but
  the `/authorize` `302` Location example shows only `code` and `state`
  (oauth-openapi.yaml:147–148); it omits the PKCE error case where
  `error=invalid_request` is returned in the redirect for a missing or
  unsupported challenge (§4.4.1). The error-redirect example
  (oauth-openapi.yaml:148) uses `error=access_denied`; add an
  `error=invalid_request` example to make the PKCE error path visible.

## NICE-TO-HAVE

- **Reusable `CodeChallenge` schema component**: extract the `code_challenge`
  string constraints (length + pattern) into
  `components.schemas.PKCECodeChallenge` and
  `components.schemas.PKCECodeVerifier`, then `$ref` from both
  `parameters.CodeChallenge`, `AuthorizationCodeTokenRequest.code_verifier`,
  and `PARRequest.code_challenge`. Removes duplication and ensures the
  PAR/authorize/token paths stay in sync if the constraints ever change.

- **Examples**: §4.6 includes a worked example (verifier
  `dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk`, S256 challenge
  `E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM`). Adding these as
  `examples:` on the verifier and challenge schemas makes the spec
  self-documenting.

- **Cross-reference §7 Security Considerations** in the parameter
  description: §7.1 (entropy of code_verifier ≥ 256 bits) and §7.2
  (protection against eavesdroppers) are useful for client implementers.

- **Discovery `require_pkce` boolean** (not in RFC 7636 itself but a
  natural fit alongside `require_pushed_authorization_requests`):
  signals that the AS rejects authorization requests without PKCE.

## NOT APPLICABLE

- **§4.1 ABNF for `code_verifier` and §4.2 ABNF for `code_challenge`**:
  pure grammar definitions. The OpenAPI `pattern` regex (suggested under
  MISSING) is the OpenAPI-equivalent expression of these ABNF rules.

- **§4.4 Server returns the authorization code as normal**: this is RFC
  6749 §4.1.2 behavior; nothing PKCE-specific to model in the OpenAPI.

- **§4.5 Server stores `code_challenge` and `code_challenge_method`**:
  internal AS state, not part of any HTTP surface.

- **§4.7 Server compares verifier**: server-side algorithm; the only
  observable surface is the success/error HTTP response, which is
  already covered by `ErrorResponse` (`invalid_grant`) and the `200`
  token response.

- **§5 Compatibility**: backwards-compatibility commentary; not normative
  schema content.

- **§6 IANA Considerations**: registration of `S256`/`plain` in the PKCE
  Code Challenge Method registry. The enum already lists both values;
  no further IANA modeling is needed.

- **§7.3–§7.6 Security Considerations**: implementation guidance
  (entropy, brute force, salting, plain-method weakness). NICE-TO-HAVE
  description text only; not OpenAPI structural elements.

- **§8 Acknowledgements** and Appendix A: non-normative.
