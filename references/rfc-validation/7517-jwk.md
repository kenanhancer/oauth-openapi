# RFC 7517 — JSON Web Key (JWK)

Source: https://datatracker.ietf.org/doc/html/rfc7517
Audit date: 2026-05-10

> Note: WebFetch and curl access to RFC 7517 were both denied during this
> audit; findings rely on the well-established normative text of RFC 7517
> (May 2015, IETF Standards Track) cross-referenced against the spec at
> `oauth-openapi.yaml`. Section citations follow the published RFC.

## Correctly modeled

- **`/jwks` endpoint exists and links to RFC 7517 §5** (oauth-openapi.yaml:418-437):
  the GET operation returns a `JWKS` schema and includes an `externalDocs`
  pointer to RFC 7517 §5 (the "JWK Set" definition). Tagged under `JWKS`.

- **`JWKS.keys` is REQUIRED and is an array of JWK objects** (§5.1, §5)
  — the spec models `JWKS` with `required: [keys]` and `keys` typed as
  `array` of `$ref: '#/components/schemas/JWK'` (oauth-openapi.yaml:1077-1084).
  This matches §5.1: "The value of the `keys` parameter is an array of JWK
  values" and the implication of §5 that `keys` is the single defined member.

- **`JWK.kty` is REQUIRED** (§4.1): the spec lists `kty` in `required: [kty]`
  (oauth-openapi.yaml:1088). §4.1 states "The `kty` (key type) parameter
  identifies the cryptographic algorithm family used with the key, such as
  `RSA` or `EC`. … This member MUST be present in a JWK."

- **`use` enum values `sig` and `enc`** (§4.2 and §8.2 IANA Public Key Use
  registry): the spec restricts `use` to `[sig, enc]` (oauth-openapi.yaml:
  1096-1098), matching the two registered values in §8.2.

- **`alg` is OPTIONAL string** (§4.4): modeled as a free-form string with
  RFC 7518 example values `RS256, ES256, EdDSA` (oauth-openapi.yaml:1103-
  1105). §4.4 "Use of this member is OPTIONAL."

- **`kid` is OPTIONAL string** (§4.5): modeled as a string
  (oauth-openapi.yaml:1106-1107). §4.5 "Use of this member is OPTIONAL.
  When used … the structure of the `kid` value is unspecified."

- **`x5u` is OPTIONAL URI** (§4.6): modeled as `string` with `format: uri`
  (oauth-openapi.yaml:1108-1110), matching §4.6 "The `x5u` (X.509 URL)
  parameter is a URI [RFC3986] that refers to a resource for an X.509 public
  key certificate or certificate chain".

- **`x5c` is OPTIONAL array of strings** (§4.7): modeled as `array` of
  `string` items (oauth-openapi.yaml:1111-1114), matching the §4.7 type
  ("a JSON array of certificate value strings").

- **RSA modulus `n` and exponent `e` (RFC 7518 §6.3.1.1, §6.3.1.2)** —
  documented as "RSA modulus (base64url)" and "RSA exponent (base64url)"
  (oauth-openapi.yaml:1119-1124). Strictly RFC 7518 territory but RFC 7517
  §4 references the algorithm-specific registry.

- **EC/OKP `crv`, `x`, `y` parameters** (RFC 7518 §6.2 / RFC 8037 §2):
  documented (oauth-openapi.yaml:1125-1131), with examples `P-256` and
  `Ed25519` covering both EC and OKP families.

## MISSING — must add

- **`OKP` value not registered by RFC 7517 — must reference RFC 8037**
  (§8.1, IANA "JSON Web Key Types"): the spec includes `OKP` in
  `kty.enum` (oauth-openapi.yaml:1095) but `OKP` is registered by RFC 8037
  §2, not RFC 7517. The schema description should cite RFC 8037 alongside
  RFC 7517 for completeness; otherwise readers may believe `OKP` is in
  RFC 7517's initial registry. (The value is correct; the citation is what
  is missing.)

- **`key_ops` value enum** (§4.3 / §8.3 IANA Key Operations registry):
  the spec types `key_ops` as a free-form `array` of `string`
  (oauth-openapi.yaml:1099-1102), but §4.3 enumerates eight registered
  values: `sign`, `verify`, `encrypt`, `decrypt`, `wrapKey`, `unwrapKey`,
  `deriveKey`, `deriveBits`. Add `items.enum` with these eight values
  (or document them in the description). §4.3 also says "Other values MAY
  be used" — so the enum must permit extension, but the eight registered
  ones should at minimum appear in `examples`.

- **`key_ops` and `use` SHOULD NOT both be used; values must be disjoint**
  (§4.3): "The `use` and `key_ops` JWK members SHOULD NOT be used together;
  however, if both are used, the information they convey MUST be
  consistent." and "Multiple unrelated key operations SHOULD NOT be
  specified". Add this constraint to the `key_ops` and `use` descriptions.

- **`x5t` is base64url-encoded SHA-1 thumbprint of DER cert** (§4.8):
  the spec models `x5t` as a bare `string` (oauth-openapi.yaml:1115-1116)
  with no description. §4.8 specifies it is the "base64url-encoded SHA-1
  thumbprint (a.k.a. digest) of the DER encoding of an X.509 certificate
  [RFC5280]". Add `description` and ideally a regex pattern
  (`^[A-Za-z0-9_-]+$`, length 27 for SHA-1).

- **`x5t#S256` is base64url-encoded SHA-256 thumbprint** (§4.9): modeled
  as a bare `string` (oauth-openapi.yaml:1117-1118). §4.9: "base64url-
  encoded SHA-256 thumbprint (a.k.a. digest) of the DER encoding of an
  X.509 certificate". Add description and ideally pattern (length 43).

- **`x5c` certificates are base64 (NOT base64url)** (§4.7): the spec lacks
  the description that §4.7 explicitly calls out — "Each string in the array
  is a base64-encoded (Section 4 of [RFC4648] -- not base64url-encoded) DER
  [ITU.X690.1994] PKIX certificate value". Without this, implementers will
  almost certainly use base64url and break interop. The first cert is the
  one matching the public key; subsequent certs form the chain.

- **`x5c` ordering** (§4.7): "The PKIX certificate containing the key value
  MUST be the first certificate. … each subsequent certificate … MUST
  certify the one preceding it." Add to description.

- **`x5u` integrity requirement** (§4.6): "The key in the first certificate
  MUST match the public key represented by other members of the JWK." and
  "The protocol used to acquire the resource MUST provide integrity
  protection". Add a security note to the `x5u` description.

- **JWK Set media type `application/jwk-set+json`** (§8.5.2): the `/jwks`
  GET response declares `content: application/json` (oauth-openapi.yaml:
  434-437). RFC 7517 §8.5.2 registers `application/jwk-set+json` as the
  media type for JWK Set documents. The endpoint SHOULD advertise this
  media type (either replacing or adding alongside `application/json`).

- **JWK media type `application/jwk+json`** (§8.5.1): registered by §8.5.1
  for a single JWK. Not directly used by the `/jwks` response (which is a
  set), but worth documenting in the `JWK` schema description so
  consumers/producers of single-JWK payloads (e.g., DPoP `jwk` header
  contents serialized standalone) know the canonical media type.

- **String comparison rules** (§6): "All comparisons … MUST be performed
  as Unicode code-point-for-code-point equality comparisons on the
  unescaped strings". This affects `kid`, `kty`, `use`, `key_ops`, `crv`
  values. Worth a single-line note on `JWK.description`.

- **`kid` uniqueness in a JWK Set** (§4.5): "When `kid` values are used
  within a JWK Set, different keys within the JWK Set SHOULD use distinct
  `kid` values". The spec's `JWKS.keys` array has no uniqueness or `kid`
  guidance — add to the `JWKS` description.

- **Private-key parameters** (RFC 7518 §6.2.2 / §6.3.2 / RFC 8037 §2):
  the spec models only public-key parameters (n, e, crv, x, y). RFC 7517
  §1 and §3 explicitly cover both public and private keys ("A JWK
  represents a cryptographic key. … Both public and private keys are
  supported."). For completeness, add the private-key parameters to the
  `JWK` schema or document why they are intentionally omitted (a JWKS
  endpoint exposes only public keys, but a `JWK` schema reused elsewhere
  — e.g., DPoP `jwk` header for a private signer — could need them). The
  parameters are: `d` (RSA/EC/OKP private exponent or private key), `p`,
  `q`, `dp`, `dq`, `qi` (RSA CRT params), `oth` (RSA additional primes),
  `k` (oct key value).

- **`oct` symmetric-key parameter `k`** (RFC 7518 §6.4.1): the spec lists
  `oct` in `kty.enum` but does not model the `k` parameter. Without `k`,
  an `oct` JWK is invalid. Add `k: string` (base64url symmetric key value).

## WRONG — must fix

- **`kty.enum` is closed at four values** (§4.1, §8.1): the spec restricts
  `kty` to `[RSA, EC, OKP, oct]` (oauth-openapi.yaml:1093-1095). §8.1
  establishes the IANA "JSON Web Key Types" registry, which is extensible
  ("Specification Required" registration policy). New `kty` values
  (e.g., `RSA-PSS` proposals, hybrid PQ keys) can and do get registered.
  Either drop the `enum` or document that it is illustrative (e.g.,
  via an `examples` array) — a hard `enum` makes the spec wrong-by-omission
  for any future or vendor-extension key type.

- **`/jwks` `200` response Content-Type is `application/json` only**
  (oauth-openapi.yaml:434-437): per §8.5.2 the canonical media type is
  `application/jwk-set+json`. Real-world implementations (Google, Auth0,
  Okta) frequently serve `application/json` for compatibility, but the
  RFC-canonical value is `application/jwk-set+json`. A spec that bills
  itself as RFC-canonical (oauth-openapi.yaml:3) should at minimum list
  both, with `application/jwk-set+json` first.

- **`x5c` items typed as plain `string` with no encoding hint** (§4.7):
  modeled as `items: { type: string }` (oauth-openapi.yaml:1112-1114).
  §4.7 mandates base64 (RFC 4648 §4) encoding, NOT base64url. Either add
  `description: 'base64-encoded (RFC 4648 §4, NOT base64url) DER X.509
  certificate'` or a `pattern` constraining to standard base64 alphabet
  (`^[A-Za-z0-9+/]+=*$`). The current model invites the most common
  interop bug in JWKS production.

- **`kty` enum value casing** is correct (`RSA`, `EC`, `OKP`, `oct`) but
  the spec lacks the §6 explicit reminder that comparisons are
  case-sensitive. Without that, a generator targeting case-insensitive
  matching could emit `rsa` and break consumers. (Listed under WRONG
  because the consequence is wire-incompatible payloads.)

## NICE-TO-HAVE

- **Per-`kty` discriminator / `oneOf` modelling**: the JWK schema
  description acknowledges the shape depends on `kty` (oauth-openapi.yaml:
  1090-1091) but does not enforce it via `oneOf` + `discriminator`. A
  more rigorous model would split `JWK` into `RsaJwk`, `EcJwk`, `OkpJwk`,
  `OctJwk` with required-parameter sets per RFC 7518 / RFC 8037, then
  compose with `oneOf` discriminated on `kty`. This is the canonical
  OpenAPI 3.1 way to express §4 + §6 + RFC 7518 §6.

- **Examples**: a worked RSA-256 public-key JWKS example and an EC P-256
  example (both appear in RFC 7517 Appendix A) would make the schema
  self-documenting.

- **Cache-Control on `/jwks`**: §5 has no requirement, but operationally
  every real JWKS endpoint sets `Cache-Control: max-age=…` so clients
  cache keys efficiently. A `headers.Cache-Control` on the 200 response
  with a reasonable example (e.g., `public, max-age=3600`) helps
  implementers.

- **ETag + 304 support on `/jwks`**: also operational, not normative;
  documenting it as a pattern would help integrators.

- **Cross-reference to RFC 7638 (JWK Thumbprint)**: while not part of
  RFC 7517, JWK Thumbprint computation is essential for the `kid` /
  `jkt` claim used by DPoP (RFC 9449). A see-also note on `kid` would
  bridge the two specs already cited in this OpenAPI.

- **`alg` enum referencing RFC 7518 §3.1 / §4.1 registries**: the spec
  uses `examples: [RS256, ES256, EdDSA]`, but a curated `enum` listing
  the canonical signing algorithms (RS256, RS384, RS512, PS256, PS384,
  PS512, ES256, ES384, ES512, ES256K, EdDSA, HS256/384/512) would catch
  typos. Trade-off: locks out new IANA-registered algorithms, so
  `examples` is the safer choice — but at minimum extend the example list.

## NOT APPLICABLE

- **§3 Example JWK and §3.1 Example Public Keys / §3.2 Example Private
  Keys**: illustrative, not normative; the schema covers the shape.

- **§7 Encrypted JWK and JWK Set**: out of scope — RFC 7517 §7 says
  "The JWK and JWK Set objects … MAY be encrypted using JWE". The spec
  models only the public-key JWKS distribution use case, which is the
  only one OAuth 2.0 / OIDC actually consume. JWE-wrapped JWK Sets are
  used for key-distribution between trusted parties out-of-band.

- **§9 Security Considerations** in their entirety: cannot be modeled
  in OpenAPI; covered indirectly by TLS requirements documented elsewhere
  in the spec (RFC 8414 / OIDC Discovery use HTTPS for `jwks_uri`).

- **§10 Internationalization Considerations**: not modelable in OpenAPI.

- **§8.1.1 / §8.2.1 / §8.3.1 Registration Templates** for IANA: registry
  procedure, not protocol surface; nothing for the spec to model.

- **§8.5.x media-type registration template fields** beyond the type
  string itself (e.g., "Macintosh File Type Code", "Author"): IANA
  bookkeeping — not protocol surface. Only the type string matters
  (`application/jwk+json`, `application/jwk-set+json`).
