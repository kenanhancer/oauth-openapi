# RFC 7519 — JSON Web Token (JWT)

Source: https://datatracker.ietf.org/doc/html/rfc7519
Audit date: 2026-05-10

> Note: WebFetch was denied during this audit; the RFC was retrieved with
> `curl https://www.rfc-editor.org/rfc/rfc7519.txt` and read directly. All
> section citations are taken verbatim from the published RFC (Standards
> Track, May 2015).

## Scope reminder

RFC 7519 only defines the **JWT format** (claims set + JOSE wrapper +
compact serialization). It does **not** define how access tokens use it —
that is RFC 9068 (JWT Profile for OAuth 2.0 Access Tokens). This audit
restricts itself to the format-level surface in `oauth-openapi.yaml`,
namely:

- `IntrospectionResponse` claims (which mirror JWT claim names per RFC 7662
  §2.2 — that section explicitly references RFC 7519 for `iss`, `sub`,
  `aud`, `exp`, `nbf`, `iat`, `jti`).
- `TokenResponse.id_token` (an OIDC ID Token, which is normatively a JWT).
- `DPoPHeader.schema.description` ("A JWT in compact serialization").
- `bearerAuth.bearerFormat: JWT`.
- The `urn:ietf:params:oauth:token-type:jwt` value in
  `TokenExchangeRequest.subject_token_type` (registered by RFC 7519 §10.2).

There are no `IDTokenClaims` or `JWTClaims` schema components in the spec;
the introspection response is the only place JWT-claim shapes are
explicitly materialized.

## Correctly modeled

- **Compact serialization referenced by name** (§3, §7.1): the
  `DPoPHeader` parameter description says "A JWT in compact serialization"
  (oauth-openapi.yaml:683). This is the correct RFC 7519 vocabulary —
  §3 specifies "a sequence of URL-safe parts separated by period ('.')
  characters" and §7.1 step 6 yields the JWS or JWE in compact form.

- **`urn:ietf:params:oauth:token-type:jwt` token type** (§10.2): the
  `TokenExchangeRequest.subject_token_type` enum
  (oauth-openapi.yaml:823–829) includes
  `urn:ietf:params:oauth:token-type:jwt`. This URN is registered by
  RFC 7519 §10.2.1 and the value matches verbatim.

- **`id_token` typed as `string`** (§3): the OIDC ID Token is delivered as
  a compact-serialization JWT (a string of three or five base64url parts
  joined by `.`), so `TokenResponse.id_token: type: string`
  (oauth-openapi.yaml:870–872) is correct.

- **`exp`, `iat`, `nbf` modeled as `integer`** (§4.1.4 / §4.1.6 / §4.1.5):
  `IntrospectionResponse.exp`, `.iat`, `.nbf` are all `type: integer`
  (oauth-openapi.yaml:1040–1047). §2 NumericDate is "A JSON numeric value
  representing the number of seconds from 1970-01-01T00:00:00Z UTC". The
  `description: Expiration time (seconds since epoch)` on `exp` matches
  the §4.1.4 NumericDate definition.

- **`aud` typed as string-or-array-of-string** (§4.1.3):
  `IntrospectionResponse.aud` uses `oneOf: [string, array of string]`
  (oauth-openapi.yaml:1050–1055). §4.1.3 says "in the general case, the
  'aud' value is an array of case-sensitive strings, each containing a
  StringOrURI value. In the special case when the JWT has one audience,
  the 'aud' value MAY be a single case-sensitive string". This polymorphism
  is captured exactly.

- **`sub`, `iss`, `jti` typed as `string`** (§4.1.2 / §4.1.1 / §4.1.7):
  all three are `type: string` in `IntrospectionResponse`
  (oauth-openapi.yaml:1048, 1056–1059). §4.1.7 says "the 'jti' value is a
  case-sensitive string"; §4.1.1/§4.1.2 say "case-sensitive string
  containing a StringOrURI value".

- **All registered claims optional in introspection**: per §4.1, none of
  the registered claims are mandatory in the JWT itself; the spec
  correctly marks only `active` as required on `IntrospectionResponse`
  (oauth-openapi.yaml:1025).

## MISSING — must add

- **No `IDTokenClaims` schema (OIDC Core §2 + RFC 7519 §4.1)**: the spec
  references `id_token` only as an opaque `type: string`
  (oauth-openapi.yaml:870–872). For an RFC-canonical spec, a companion
  `IDTokenClaims` object schema documenting the registered RFC 7519
  claims (`iss`, `sub`, `aud`, `exp`, `nbf`, `iat`, `jti`) plus the OIDC
  Core §2 additions (`auth_time`, `nonce`, `acr`, `amr`, `azp`) should
  exist so that an OpenAPI consumer understands the *payload* of the
  signed JWT, not merely that a string is returned. Suggested name:
  `components.schemas.IDTokenClaims`.

- **No `JWTAccessTokenClaims` schema (RFC 7519 §4.1 + RFC 9068)**: the
  `access_token` field is also typed as `string` (oauth-openapi.yaml:
  852–855). When the AS issues JWT access tokens, the payload follows
  RFC 9068, but its claim surface is the RFC 7519 §4.1 set. A claims
  schema referenced from the description would help. (Out of strict scope
  for 7519 alone, but flagged here because it directly uses the §4.1
  registered names.)

- **`StringOrURI` constraint not surfaced** (§2): RFC 7519 §2 defines
  `StringOrURI` — "A JSON string value, with the additional requirement
  that while arbitrary string values MAY be used, any value containing a
  ':' character MUST be a URI [RFC3986]". The `iss`, `sub`, `aud`
  properties on `IntrospectionResponse` say `type: string` only. They
  should either (a) describe the StringOrURI rule in the field
  `description`, or (b) define a reusable
  `components.schemas.StringOrURI` (`type: string`, with a description
  citing §2) and `$ref` it. Same applies to the array-element schema for
  `aud`.

- **`NumericDate` reusable type not defined** (§2): §2 defines
  `NumericDate` as "A JSON numeric value representing the number of
  seconds from 1970-01-01T00:00:00Z UTC ... non-integer values can be
  represented." The spec uses `type: integer` for `exp`, `iat`, `nbf`,
  which is **too narrow** — see WRONG below. A reusable
  `components.schemas.NumericDate` (`type: number`, format `int64` or no
  format, description citing §2) would let the spec be precise.

- **No description of compact serialization on `id_token`,
  `access_token`, `assertion`, `subject_token`, `actor_token`, `request`,
  `id_token` in TokenExchangeRequest**: every field that carries a JWT is
  typed as `type: string` with no hint that it must be compact JWS/JWE
  serialization. Only `DPoPHeader` (oauth-openapi.yaml:683) and the
  `description` of `assertion` (oauth-openapi.yaml:807, "A signed JWT
  bearer assertion") allude to it. Add a one-line note like "JWS/JWE
  compact serialization per RFC 7519 §3" on each.

- **No documentation of duplicate-claim handling** (§4): "The Claim Names
  within a JWT Claims Set MUST be unique; JWT parsers MUST either reject
  JWTs with duplicate Claim Names or use a JSON parser that returns only
  the lexically last duplicate member name". This is a parser-side rule
  but worth noting in any JWT-related field description so vendors know
  the AS-side requirement.

## WRONG — must fix

- **`exp`, `iat`, `nbf` typed as `integer` instead of `number`** (§2,
  §4.1.4–§4.1.6): all three §4.1.x sections say "Its value MUST be a
  number containing a NumericDate value", and §2 NumericDate explicitly
  permits "non-integer values can be represented" (sub-second precision).
  Restricting to `integer` excludes valid NumericDate values such as
  `1300819380.5`. Fix: change `type: integer` to `type: number` on
  `IntrospectionResponse.exp`, `.iat`, `.nbf` (oauth-openapi.yaml:1040,
  1043, 1046). In practice 99% of issuers emit integer seconds, but the
  RFC permits fractional seconds and a strict spec should not exclude
  them.

- **`bearerFormat: JWT` overstates RFC 7519's role**
  (`securitySchemes.bearerAuth`, oauth-openapi.yaml:1315–1319): RFC 7519
  defines the format; whether the AS issues JWT bearer tokens vs. opaque
  tokens is determined by RFC 9068 (or vendor choice). This is also
  flagged in the RFC 6750 audit; from the RFC 7519 perspective, the issue
  is that listing `JWT` as the bearer format implicitly *promises* the
  payload will be a JWT Claims Set (§4) without referencing §4 anywhere
  in the spec. Either remove `bearerFormat: JWT` or add a description
  noting that when the bearer is a JWT, its claims follow RFC 7519 §4 +
  RFC 9068.

- **`IntrospectionResponse` field descriptions lack RFC 7519 citations**
  (oauth-openapi.yaml:1040–1059): `exp`, `iat`, `nbf`, `sub`, `aud`,
  `iss`, `jti` are all RFC 7519 §4.1.x registered claims, but the
  descriptions cite only RFC 7662 (the introspection RFC). Add `(RFC 7519
  §4.1.N)` annotations so the lineage is visible — RFC 7662 §2.2 itself
  says "The following is a list of claims that are commonly included in
  the response ... All other claims are listed in the JSON Web Token
  (JWT) specification [RFC7519]".

## NICE-TO-HAVE

- **Reusable `JWT` string schema with description**: many fields
  (`id_token`, `access_token` when JWT, `assertion`, `subject_token`,
  `actor_token`, `request`, the `DPoP` header) all carry a JWT in compact
  serialization. A single `components.schemas.JWT` (`type: string`,
  description citing RFC 7519 §3 and §7.1) `$ref`d from each would make
  the spec drier and self-documenting.

- **`StringOrURI` as a reusable schema**: same argument — `iss`, `sub`,
  `aud`-element are all StringOrURI. Defining once and referencing keeps
  the §2 semantics in one place.

- **JOSE Header `typ`/`cty`/`alg` documentation** (§5.1, §5.2): the spec
  never models the JOSE Header. It does not need to (the header lives
  inside the JWT string, not in the OpenAPI request/response surface),
  but a short note in the `JWT` description recommending `typ: "JWT"`
  (§5.1) and the §5.2 rule that nested JWTs MUST have `cty: "JWT"` would
  be useful documentation.

- **Note `alg: "none"` is an Unsecured JWT** (§6): the
  `id_token_signing_alg_values_supported` array
  (oauth-openapi.yaml:1209–1212) is freeform `string`. A description
  noting that `none` is permitted by §6 but is essentially never
  acceptable in OAuth/OIDC contexts (per RFC 9700 / OIDC Core §16.18)
  would help readers.

- **§7.3 string comparison rules**: when listing claim values, note that
  RFC 7519 §7.3 mandates case-sensitive byte-by-byte comparison for
  StringOrURI values (with `typ`/`cty` as the only exceptions). Helpful
  for implementers writing claim-validation code from the spec.

- **§4 unique-claim-name parser requirement** (see MISSING) is also
  reasonable to surface as a note rather than a separate field.

## NOT APPLICABLE

- **§3.1 example JWT, §6.1 example unsecured JWT, Appendix A.1/A.2
  examples**: illustrative, not normative; OpenAPI examples for `id_token`
  / `access_token` are sufficient.

- **§5.3 Replicating Claims as Header Parameters**: applies inside the
  JWT envelope, not at the HTTP surface; no OpenAPI modeling needed.

- **§7.1 / §7.2 creating and validating steps**: implementation algorithms
  for JWT producers and consumers; outside the API surface.

- **§8 Implementation Requirements** (HS256 + none MUST be implemented;
  RS256, ES256 RECOMMENDED): a property of the JWT *library*, not of the
  HTTP API. The spec already exposes algorithm choices via
  `id_token_signing_alg_values_supported` (oauth-openapi.yaml:1209–1212),
  which is the right level of abstraction.

- **§9 URI for declaring content is a JWT** (`urn:ietf:params:oauth:
  token-type:jwt`): IANA-registered URN; the spec already includes it in
  the token-exchange enum (oauth-openapi.yaml:829).

- **§10 IANA Considerations** (claims registry, media type `application/
  jwt`, header parameter names): registries, not API surface. The
  `application/jwt` media type is correctly used on `/userinfo` GET
  (oauth-openapi.yaml:385–388).

- **§11 Security Considerations / §12 Privacy Considerations**: best-
  practice text; reflected at the protocol layer by RFC 9700 references
  in the spec preamble.

- **Appendix B (SAML), Appendix C (SWT)**: comparative material, no API
  surface impact.
