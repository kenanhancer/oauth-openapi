# RFC 9449 — OAuth 2.0 Demonstrating Proof of Possession (DPoP) — Validation Report

Source: <https://datatracker.ietf.org/doc/html/rfc9449>
Spec under review: `oauth-openapi.yaml` — `parameters.DPoPHeader` (line 673),
`securitySchemes.dpop` (line 1321), `ErrorResponse.error` enum (line 882),
`TokenResponse.token_type` (line 856), `DiscoveryDocument` (line 1136),
`/token` and `/par` (lines 159, 326), `/userinfo` (line 367).

> Note: WebFetch was denied during this audit. Findings cite RFC 9449
> (September 2023, IETF Standards Track) directly from the canonical
> plaintext at `references/rfc-validation/.rfc9449-source.txt` (downloaded
> from rfc-editor.org). All section citations are verbatim from that text.

---

## Summary

| Bucket  | Count |
| ------- | ----- |
| MISSING | 11    |
| WRONG   | 4     |
| EXTRA   | 0     |

The spec acknowledges DPoP exists (header parameter, security scheme, two
error codes, metadata field, `token_type=DPoP` example), but stops well
short of modeling the protocol as RFC 9449 defines it. The DPoP proof JWT
schema, the `cnf.jkt` confirmation method, the `dpop_jkt` authorization
parameter, the `DPoP-Nonce` response header, the `dpop_bound_access_tokens`
client-registration field, and the `WWW-Authenticate: DPoP` challenge
syntax are all absent. Additionally, the `securitySchemes.dpop` declaration
uses `scheme: dpop`, which is not a registered HTTP authentication scheme
recognised by Swagger UI / Scalar tooling — only `bearer`, `basic`, `digest`,
etc. are valid `http` scheme values.

---

## MISSING (RFC element absent from the OpenAPI spec)

### M1. DPoP proof JWT structure not modeled (§4.2)

§4.2 normatively specifies the DPoP proof JWT's JOSE Header (`typ="dpop+jwt"`,
asymmetric `alg`, public-key-only `jwk`) and its claim set
(`jti`, `htm`, `htu`, `iat`, optional `ath` at the resource server, optional
`nonce`). The spec models the carrying header (`parameters.DPoPHeader`,
oauth-openapi.yaml:673–684) but the body of the JWT itself is opaque
(`type: string, description: A JWT in compact serialization`). A reader
of the OpenAPI cannot discover any of the required fields.

**Fix:** add `components/schemas/DPoPProofJWT` documenting header (`typ`,
`alg`, `jwk`) and payload (`jti`, `htm`, `htu`, `iat`, `ath`, `nonce`) and
reference it from `DPoPHeader.description`. Even though the wire form is a
compact JWS string, an OpenAPI-canonical spec should describe the decoded
shape — the same pattern already used for `id_token` would suffice.

### M2. `cnf.jkt` confirmation method (§6.1) not modeled in `IntrospectionResponse`

§6.1: *"the public key information is represented using the `jkt` confirmation
method member ... The value of the jkt member MUST be the base64url encoding
... of the JWK SHA-256 Thumbprint."* §6.2 specifies the same `cnf.jkt` is
returned in the introspection response for DPoP-bound tokens.
`IntrospectionResponse` (oauth-openapi.yaml:1022–1059) has no `cnf` field,
so a resource server cannot discover from this OpenAPI spec how to obtain
the DPoP key binding for an opaque token.

**Fix:** add `cnf: { type: object, properties: { jkt: { type: string,
description: "JWK SHA-256 Thumbprint, base64url (RFC 9449 §6.1)" } } }` to
`IntrospectionResponse`. Same `cnf` claim shape should also be referenced
from any documentation of access-token JWT contents (see also RFC 9068).

### M3. `dpop_jkt` authorization-request parameter (§10) not modeled

§10: *"This specification defines the `dpop_jkt` authorization request
parameter ... When a token request is received, the authorization server
computes the JWK Thumbprint of the proof-of-possession public key in the
DPoP proof and verifies that it matches the dpop_jkt parameter value."*
The `/authorize` parameters list (oauth-openapi.yaml:117–134) contains no
`dpop_jkt`, and `PARRequest` (oauth-openapi.yaml:963–990) similarly lacks
it.

**Fix:** add `parameters.DpopJkt` (`name: dpop_jkt, in: query, required:
false, schema: { type: string }`) and `$ref` it from `/authorize`. Add an
identically-named property to `PARRequest`. §10.1 makes this MUST be
supported by any AS that supports both PAR and DPoP.

### M4. `DPoP-Nonce` response header (§§8, 9) not modeled

§8 / §9: an authorization or resource server MAY supply a nonce via the
`DPoP-Nonce` HTTP response header on either the 400/401 nonce-required
error or the 200 OK ("more efficient manner of supplying a new nonce
value"). The spec declares no `DPoP-Nonce` header on any response.

**Fix:** add `components/headers/DPoPNonce` with `schema: { type: string,
pattern: "^[\\x21-\\x7E]+$" }` and a description quoting §8.1's `nonce =
1*NQCHAR` ABNF, then attach it to `/token` 200, `/token` 400, `/par` 201,
`/par` 400, `/userinfo` 200, and `/userinfo` 401 responses.

### M5. `dpop_bound_access_tokens` client-registration metadata (§5.2) not present

§5.2 / §12.10 (IANA registration): *"`dpop_bound_access_tokens`: A boolean
value specifying whether the client always uses DPoP for token requests.
If omitted, the default value is false. If the value is true, the
authorization server MUST reject token requests from the client that do
not contain the DPoP header."* The spec has no client-registration schema
at all (RFC 7591 is out of scope per the cover sheet), but the discovery
document and the `dpop` security scheme description should at least
mention this field exists; otherwise an implementer reading this spec for
DPoP semantics has no path to discover it.

**Fix:** add a `description` note on `securitySchemes.dpop` referencing
RFC 9449 §5.2 and the `dpop_bound_access_tokens` client metadata.

### M6. `WWW-Authenticate: DPoP` challenge syntax not modeled (§7.1)

§7.1 normatively defines the `WWW-Authenticate: DPoP …` challenge for
401 responses to DPoP-protected resources, with the `realm`, `scope`,
`error`, `error_description`, and `algs` parameters. The `algs` parameter
is unique to DPoP (it does not appear in RFC 6750). `/userinfo` declares
`401: $ref: '#/components/responses/OAuthError'` (oauth-openapi.yaml:389,
410) but `OAuthError` carries only the JSON body — no `WWW-Authenticate`
header. This same gap was flagged in the RFC 6750 audit; it must be
extended for DPoP with the additional `algs` parameter.

**Fix:** add `components/headers/WWWAuthenticateDPoP` with a description
listing the five challenge parameters and citing §7.1, and reference it
on every 401/403 of any DPoP-supporting endpoint.

### M7. `algs` challenge parameter (§7.1) not surfaced anywhere

§7.1: *"An `algs` parameter SHOULD be included to signal to the client
the JWS algorithms that are acceptable for the DPoP proof JWT."* The same
information is exposed at the AS via `dpop_signing_alg_values_supported`
(modeled, line 1230), but RS-side `algs` discovery happens only via the
challenge header — which the spec does not model (M6).

**Fix:** document `algs` in the `WWWAuthenticateDPoP` header description
once M6 is addressed.

### M8. `dpop` security scheme not attached to `/token`, `/par`, `/introspect`, `/revoke`

§5: *"To request an access token that is bound to a public key using
DPoP, the client MUST provide a valid DPoP proof JWT in a DPoP header
when making an access token request to the authorization server's token
endpoint. This is applicable for all access token requests regardless of
grant type."* §10.1: PAR endpoint MUST support both `dpop_jkt` body field
and `DPoP` header. `/userinfo` lists `dpop: []` under `security`
(oauth-openapi.yaml:393, 413), but `/token` (line 208) and `/par` (line
359) do not — so an OpenAPI consumer would conclude DPoP at `/token` is
not supported. The `DPoPHeader` parameter is added to both, but `security`
is the *normative* declaration.

**Fix:** add `- dpop: []` to the `security` arrays of `/token` and `/par`.
Optionally add to `/introspect` and `/revoke` (DPoP at these endpoints is
not normatively required, but resource-server clients MAY use DPoP).

### M9. Refresh-token DPoP-binding rule (§5) not documented

§5: *"When an authorization server supporting DPoP issues a refresh token
to a public client that presents a valid DPoP proof at the token endpoint,
the refresh token MUST be bound to the respective public key. The binding
MUST be validated when the refresh token is later presented to get new
access tokens. As a result, such a client MUST present a DPoP proof for
the same key that was used to obtain the refresh token each time that
refresh token is used to obtain a new access token."* The `RefreshToken
Request` schema (oauth-openapi.yaml:767–781) and the `/token` description
(oauth-openapi.yaml:163–179) do not mention this MUST.

**Fix:** add a sentence to the `/token` description and/or to
`RefreshTokenRequest` description noting the §5 refresh-token-binding rule
for public clients with DPoP.

### M10. `application/dpop+jwt` media type (§12.5) not declared

§12.5: IANA registers `application/dpop+jwt` as the media type for a DPoP
proof JWT. The spec describes `DPoPHeader` only as *"A JWT in compact
serialization"* with no `format`/media-type hint.

**Fix:** add `description` text on `DPoPHeader` referencing
`application/dpop+jwt` and `typ="dpop+jwt"` from §4.2 / §12.5. (Headers
do not carry Content-Type negotiation, but the description is the right
place to surface the registered media type.)

### M11. No `400` response carrying `use_dpop_nonce` modeled at AS endpoints (§8)

§8: *"the authorization server responds to requests that do not include
a nonce with an HTTP 400 (Bad Request) error response per Section 5.2 of
[RFC6749] using `use_dpop_nonce` as the error code value. The
authorization server includes a DPoP-Nonce HTTP header in the response."*
The error code is in the `ErrorResponse.error` enum (line 906), but the
response example/header binding is not. This is the combination of M4
(missing `DPoP-Nonce` header) and the absence of any operation-level
guidance pointing the implementer at the §8 nonce handshake.

**Fix:** add a 400 response example on `/token` showing
`{ "error": "use_dpop_nonce" }` paired with the `DPoP-Nonce` header.

## WRONG (RFC element present but modeled incorrectly)

### W1. `securitySchemes.dpop` uses `scheme: dpop` — invalid in OpenAPI 3.1 / fragile in tooling (§7.1)

The spec declares (oauth-openapi.yaml:1321–1326):

```yaml
dpop:
  type: http
  scheme: dpop
  description: |
    DPoP-bound access token. Both an `Authorization: DPoP <token>` header
    AND a `DPoP: <proof-jwt>` header are required (RFC 9449).
```

OpenAPI 3.1 / 3.0.x's `http` security scheme expects the `scheme` value
to be an HTTP Authentication Scheme registered with IANA (§16.4.1 of RFC
9110, where DPoP is now registered per §12.4). In practice, however,
Swagger UI, Scalar, and Redoc only render `bearer`, `basic`, and `digest`
correctly; `scheme: dpop` is silently treated as Bearer or rejected. This
is also semantically incomplete because RFC 9449 requires *two* headers
(`Authorization: DPoP <token>` AND `DPoP: <proof-jwt>`) and OpenAPI's
`http`/`apiKey` security types each model only one.

**Fix:** model DPoP as a composite — either:
1. Switch to `type: apiKey, in: header, name: Authorization` with an
   explicit description of the `DPoP <token>` value AND keep `DPoPHeader`
   as a second required header on each operation, OR
2. Document on each protected operation that BOTH the `Authorization` and
   `DPoP` headers are required, with the security-scheme entry serving
   only as a marker.

§7.1 also notes the scheme MUST NOT be used with `Proxy-Authenticate` /
`Proxy-Authorization`; this could be added to the description.

### W2. `Cache-Control: no-store` on `/token` 200 lacks `DPoP-Nonce` companion (§8.2)

§8.2: *"Responses that include the DPoP-Nonce HTTP header should be
uncacheable (e.g., using `Cache-Control: no-store`)."* The spec already
declares `Cache-Control: no-store` on `/token` 200 (oauth-openapi.yaml:
191–199), which is correct, but does not declare a `DPoP-Nonce` header
alongside it (M4). Once M4 is added, the existing cache-control header
satisfies §8.2 without further change — flagging here so the connection
is documented in the spec's description.

**Fix:** when adding `DPoP-Nonce` (M4), add a description note to the
`/token` 200 response citing §8.2.

### W3. `parameters.DPoPHeader.required: false` on `/token` is correct only for the not-using-DPoP case; but the spec offers no way to mark it required when the client *is* DPoP-binding (§5)

§5: *"the client MUST provide a valid DPoP proof JWT in a DPoP header
when making an access token request"* — i.e., DPoP at `/token` is
conditionally MUST. Modeling the header as `required: false` and pinning
the requirement to whether `dpop` security is selected is the correct
OpenAPI shape, but the spec's description does not state this
conditionality. A reader sees `required: false` on `DPoPHeader` and
infers the proof is always optional.

**Fix:** rewrite `DPoPHeader.description` to: *"Conditionally REQUIRED:
when the client is requesting a DPoP-bound access token (`token_type=DPoP`
in the response), this header MUST be present (RFC 9449 §5). Otherwise
omitted."* The same text applies on `/par` (§10.1).

### W4. `DPoPHeader.schema.format` missing — should hint at JWT compact form

§4.1 ABNF: `DPoP = token68`, with `token68 = 1*( ALPHA / DIGIT / "-" /
"." / "_" / "~" / "+" / "/" ) *"="`. The spec says `type: string` only;
adding `pattern: "^[A-Za-z0-9._~+/-]+=*$"` (token68) or at minimum
`format: jwt` would convey the constraint.

**Fix:** add `pattern` (per §4.1 ABNF) to `DPoPHeader.schema` and/or note
`format: jwt` for tooling that recognises it. Same applies for the
`Authorization: DPoP <token>` value.

## Notes / out of scope

- `dpop_signing_alg_values_supported` (line 1230) is correctly modeled as
  metadata (§5.1 / §12.9). Good — this is the only DPoP element fully
  correct in the spec.
- `ErrorResponse.error` enum includes `invalid_dpop_proof` and
  `use_dpop_nonce` (lines 905–906), matching the §12.2 IANA registrations.
  Good.
- `TokenResponse.token_type` lists `DPoP` as an example value (line 859).
  Good — matches §5 / §12.1 (the IANA-registered Access Token Type
  "DPoP").
- §11 (Security Considerations) is wholly informational; nothing to model
  in OpenAPI, but a `description` note on `securitySchemes.dpop`
  acknowledging §11.1 (replay), §11.2 (pre-generation), §11.5 (signed
  JWT swapping), and §11.7 (request integrity) would help implementers.
- §7.2 (compatibility with Bearer): the spec correctly lists
  `bearerAuth: []` AND `dpop: []` on `/userinfo` (lines 391–393, 411–413),
  which is exactly the §7.2 pattern. The §7.2 RECOMMENDED challenge
  layering rules (rules in §7.2 bullet list, Figures 17–19) belong in
  description text rather than schema.
- §6.2 introspection-side `cnf.jkt`: tracked under M2.
- §10.1 PAR-and-DPoP MUST-support-both-mechanisms rule: tracked under M3
  + M8 (need both `dpop_jkt` body parameter AND `DPoP` header on /par).
- DPoP for the device authorization flow: §5 says "all grants" but the
  spec attaches `DPoPHeader` only to `/token` (line 181) and `/par` (line
  341). Strictly, since `/device_authorization` does not issue tokens
  (the token comes later from `/token`), it does not need `DPoPHeader`.
  Status: spec is correct here.
- The `Nonce` parameter at `/authorize` (line 581) is the OIDC ID-token
  `nonce`, NOT the DPoP nonce — §9.7.1 / §12.7.1 expanded the IANA
  registration to cover both meanings, but they are operationally
  distinct. The spec does not conflate them — good.
