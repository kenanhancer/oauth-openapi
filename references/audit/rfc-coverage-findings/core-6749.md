## RFC 6749 The OAuth 2.0 Authorization Framework

*October 2012 · Proposed Standard (obsoletes RFC 5849; updated by RFC 8252, RFC 8996, RFC 9700) · YAML coverage: **mostly** · relevance to an AS: required-oauth21 · vendoring: already-vendored*

**What it is.** RFC 6749 defines OAuth 2.0. Instead of giving an app their password, a resource owner approves a request at an authorization server, which issues the client a scoped, time-limited access token that the client then presents to a resource server. The RFC specifies the authorization endpoint (reached by browser redirect), the token endpoint (a back-channel POST) and the client's redirection endpoint. It also defines four grants (authorization code, implicit, resource-owner password, client credentials) plus refresh tokens, client types and client authentication, the JSON token and error responses, and the IANA registries that every later extension plugs into. It is deliberately a framework: token formats, token presentation (RFC 6750), discovery and registration are left to companion specs. It has since been updated by RFC 8252 (native apps), RFC 8996 (TLS 1.0/1.1 banned) and RFC 9700 (security BCP), and OAuth 2.1 (draft-16) is consolidating it.

**Why it was created.** Before OAuth, a third-party app that wanted your photos or mail asked for your password (the 'password anti-pattern'). It stored the password in clear text, gained unlimited and non-expiring access, could not be revoked on its own, and any breach of the app exposed the password and everything it protected (RFC 6749 §1). OAuth 1.0 (RFC 5849, 2010) introduced delegated tokens, but its per-request signatures were hard to implement and it fit only server-side web apps. OAuth 2.0, which built on OAuth WRAP, replaced signatures with TLS-protected bearer tokens. It separated the authorization server from the resource server, added flows for browser, native and server-to-server clients, and made grants, parameters, token types and error codes extensible through registries.

1. **[HIGH] Incorrect: L720-727 components.parameters.RedirectUri.description**  
   *Reference:* RFC 6749 §3.1.2.3 as updated by RFC 8252 §7.3, §8.4 and RFC 9700 §2.1, §4.1.3 (OAuth 2.1-16 §2.3.1, §8.4.2)

   *Verifier: confirmed.*

2. **[MEDIUM] Gap: Client-authentication duties per grant: client_credentials is for confidential clients only, and confidential clients MUST authenticate at /token**  
   *Reference:* RFC 6749 §4.4, §4.4.2, §3.2.1, §4.1.3, §6 (OAuth 2.1-16 §4.2, §4.2.1)

   *Suggested change:* Add to components.schemas.ClientCredentialsTokenRequest.description: 'Confidential clients only (RFC 6749 §4.4). The request MUST carry exactly one client credential: Authorization: Basic, mTLS, client_id+client_secret, or client_assertion. The empty {} security option is not acceptable for this grant; otherwise answer 401 invalid_client (§5.2).' Add to paths./token.post.description: 'Confidential clients and clients issued credentials MUST authenticate on every grant (RFC 6749 §3.2.1). {} is reserved for public clients (authorization_code with PKCE, refresh_token, device_code).'  
   *Verifier: partially correct —* The gap is real: none of §4.4 (client_credentials is confidential-only), §4.4.2 (the client MUST authenticate and the AS MUST authenticate it), or §3.2.1/§4.1.3/§6 (confidential clients MUST authenticate) is stated in the YAML. Keep {} on /token, because it carries client_secret_post and client_assertion. Fix it in prose instead: in ClientCredentialsTokenRequest and the /token description, say that this grant requires exactly one client credential (a Basic header, an mTLS certificate, client_id+client_secret in the body, or client_assertion), that public clients get unauthorized_client or invalid_client, and that a missing credential returns invalid_client (§5.2). 3. **[MEDIUM] Gap: client_secret_basic encoding: form-urlencode client_id and client_secret before Base64**  
   *Reference:* RFC 6749 §2.3.1 and Appendix B (OAuth 2.1-16 §2.4.1; reported errata 4749 and 6017)  
   Under §2.3.1, the client identifier and the client password are each first encoded with the application/x-www-form-urlencoded algorithm (Appendix B: UTF-8, then percent-escaping, with space as '+'). Only then are they used as the Basic user-id and password, and the AS 'MUST support' this scheme. securitySchemes.clientSecretBasic (L2662-2674) only says 'HTTP Basic with client_id:client_secret', and WWWAuthenticateBasic (L1026-1037) points to RFC 7617. An implementer following the YAML will Base64-decode, split on ':' and compare raw strings. That fails for every compliant client whose id or secret contains ':', '+', '/', '=', '%', '&' or non-ASCII characters, which includes any standard-Base64 secret. OAuth 2.1-16 §2.4.1 singles this out as a chronic interoperability bug.  
   *Suggested change:* Append to components.securitySchemes.clientSecretBasic.description: 'Encoding (RFC 6749 §2.3.1 and Appendix B): user-id = form-urlencode(client_id), password = form-urlencode(client_secret), credentials = base64(user-id ":" password). The AS reverses this: base64-decode, split at the first ":", then form-urldecode each half as UTF-8. Example: client_id s6BhdRkqt3 with secret 7Fjfp0ZBr1KtDRbnfVdmIw gives Basic czZCaGRSa3F0Mzo3RmpmcDBaQnIxS3REUmJuZlZkbUl3. client_id "client:1" with secret "p@ss w+rd%" becomes client%3A1:p%40ss+w%2Brd%25, which gives Basic Y2xpZW50JTNBMTpwJTQwc3MrdyUyQnJkJTI1.' Also note that OAuth 2.1-16 §2.4.1 makes client_secret_post MUST-support and Basic MAY, so the AS should support both.  
   *Verifier: confirmed.*

4. **[MEDIUM] Gap: Which /authorize errors are redirected and which get the error page**  
   *Reference:* RFC 6749 §3.1.1, §4.1.2.1 (as updated by RFC 9700 §4.11.2)  
   §3.1.1 says a missing or not-understood response_type MUST produce the §4.1.2.1 error response. §4.1.2.1 sends every failure other than a missing or invalid redirect_uri or client_id back to the client's redirect URI with error=invalid_request, unauthorized_client, access_denied, unsupported_response_type, invalid_scope, server_error or temporarily_unavailable. The YAML puts strict schema constraints on /authorize query parameters: ResponseType enum (L703-706), Scope pattern (L744), CodeChallenge length and pattern (L775-778), CodeChallengeMethod enum (L795), Prompt enum (L815-819), ResponseMode enum (L855) and Display enum (L906). Its only non-redirect error is the 400 page (L196-205), and nothing says which errors must be redirected instead. A server generated with request validation, which is the repo's stated workflow, would answer response_type=token or an invalid scope with a 400 page instead of redirecting with unsupported_response_type or invalid_scope. RFC 9700 §4.11.2 adds that the AS MUST authenticate the user before such redirects (except silent authentication) and SHOULD redirect automatically only to redirect URIs it trusts. This finding is about documenting the error-routing rule, not the intentional caveat that OpenAPI cannot model the redirect itself.  
   *Suggested change:* Add a 'Processing order' note to paths./authorize.get.description. Step 1: validate client_id and redirect_uri; a failure returns the 400 page and never redirects (§4.1.2.1, §3.1.2.4). Step 2: every other failure, including schema violations of response_type, scope, code_challenge or prompt, is returned by 302/303 to the redirect URI with the matching §4.1.2.1 code plus state and iss. Mapping: missing response_type gives invalid_request, an unsupported value gives unsupported_response_type, a bad scope gives invalid_scope, missing PKCE gives invalid_request. Generic request validation must not return 400 for these. Mention the RFC 9700 §4.11.2 precautions in the 302 description, and add an AuthorizationErrorCode enum (the seven §4.1.2.1 codes plus the OIDC §3.1.2.6 codes) that the 302 description references.  
   *Verifier: confirmed.*

   *Reference:* RFC 6749 §3.1.2, §3.1.2.2, §3.1.2.3; RFC 9700 §2.6; RFC 8252 §7, §7.1, §8.4 (OAuth 2.1-16 §2.3, §2.3.1)

   *Reference:* RFC 6749 §3.1, §3.2, §4.1.2.1, §5.2 (verified erratum 5708; reported errata 8790/8791; OAuth 2.1-16 §3.1)  
   §3.1 and §3.2 say 'Parameters sent without a value MUST be treated as if they were omitted', the AS 'MUST ignore unrecognized request parameters', and parameters defined by RFC 6749 MUST NOT be repeated (erratum 5708).
